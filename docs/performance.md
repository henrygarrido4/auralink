# Performance

Laboratory performance measurement for the production build, with regression budgets. Everything on this page is Lighthouse lab data collected on a developer machine: it predicts nothing about real users, and field Core Web Vitals (including INP, which Lighthouse cannot measure) only exist once the live site has traffic and a field data source such as the Chrome User Experience Report or a real-user monitoring tool. The starter baseline below describes an almost empty page; it is a floor for regressions, not a forecast for the finished website.

## How to run

| Command                                                          | What it does                                                                                                                                                                                        |
| ---------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `npm run perf:audit`                                             | Builds, serves `dist/` on port 4323 with `astro preview --ignore-lock`, audits every built route in mobile and desktop mode three times each, keeps the median run, writes reports, checks budgets  |
| `node scripts/perf-audit.mjs --no-build`                         | Same against the existing `dist/`                                                                                                                                                                   |
| `node scripts/perf-audit.mjs --no-build --sample`                | Same, for every top-level page and, from each directory of detail pages built from one template, only the page with the largest HTML (used by `npm run quality:full` and CI after one shared build) |
| `npm run perf:audit:quick`                                       | One run per route and device against the existing build; for quick comparisons only                                                                                                                 |
| `node scripts/perf-audit.mjs --no-build --routes=/services/seo/` | Audit specific routes (for example before and after adopting a component)                                                                                                                           |

Output: `reports/lighthouse/<timestamp>/` holds one HTML and one JSON report per run plus `summary.json` and `summary.md`; `reports/lighthouse/latest/` holds copies of the latest summary and the median reports. The folder is gitignored. The script exits 1 when any budget is exceeded. It refuses to start if port 4323 is busy so that a dev server is never measured. The summary's transfer column is the site's own resources; what a third party sends (Google Tag Manager's container script on every page, the contact page's Calendly scheduler) follows in parentheses and counts only as third-party requests (see "Budgets").

Coverage (2026-11-20): CI and `npm run quality:full` audit the sample, not every route. Pages built from one template (`src/pages/services/[slug].astro`, `src/pages/industries/[slug].astro`) share their stylesheet, fonts, scripts, and layout, so the fullest page of each directory stands for the rest, and the audit no longer grows with every page: thirty routes, three runs on two devices each, took the CI job past its time limit the day the detail pages arrived ([run 44835752855](https://github.com/henrygarrido4/auralink/actions/runs/44835752855), cancelled after fifteen minutes in that step). `npm run perf:audit` still audits every route; run it, or `--routes=<route>`, when a detail page's own data adds images or scripts, since the sample does not see that page. The summary names the coverage it was made with.

## Findings

- The starter page is a single HTML document, one stylesheet (Tailwind plus daisyUI themes, about 31 KB before compression), and no JavaScript. All four categories score 1.0 on both devices; LCP is the text heading and paints at the first contentful paint.
- There is nothing to optimise yet. The value of this baseline is the harness: every page added later is audited the same way (in CI through the sample described under "How to run"), and the budgets below define when a regression needs attention.
- Watch items as the site grows: web fonts (self-host, subset, `font-display: swap`), hero imagery (`astro:assets`, explicit dimensions, `fetchpriority="high"` on one image), island JavaScript (hydrate lazily, keep script transfer under budget), Inspira effects (canvas and WebGL effects are the likeliest budget breakers), third-party scripts (none allowed without a decision).

The mobile metric budgets are the "good" thresholds of the Core Web Vitals and Lighthouse's scoring curve; the desktop budgets are tighter because the desktop preset removes most throttling. Transfer budgets are first estimates for a marketing site with a hero image and one or two islands per page, and they cover the site's own resources, those served from the page's origin. Since 2026-11-22 the stylesheet is inlined in every page's head (`docs/architecture.md`, "Page delivery"), so `document` carries it and `stylesheet` reads 0; the document budget is what guards the sheet's size now. The rest: what a third party's script or embed fetches counts toward the third-party request budget only, and the summary reports its bytes beside the page's. ## Reading a failure

1. Open `reports/lighthouse/latest/summary.md` for the failing route and device, then the matching `*.report.html` for the audit details.
2. Compare the median run with the other runs in the timestamped folder; a single noisy run does not fail the budget, the median does.
3. Fix the page rather than the budget: image sizing and format, font loading, script hydration strategy, layout reservation for late content.
4. Re-run with `node scripts/perf-audit.mjs --no-build --routes=<route>` after `npm run build`.
