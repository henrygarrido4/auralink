# Architecture

The Auralink Studio website is a statically generated Astro site. Every page is rendered to HTML at build time, served by Netlify from `dist/`, and enhanced with small Vue islands only where interaction is required. There is no application backend, database, or authentication.

## Booking and the contact tabs (2026-11-20)

The owner asked for two ways in on the contact page, booking the free discovery call or sending the inquiry, and approved the address, the number, and the Calendly event for display (`contactDetails` and `contactRoutes` in `src/data/site.ts`; `docs/content-strategy.md`, "Contact page: booking and messages").

**Tabs without an island.** `ContactOptions.astro` renders both panels in the HTML, one after the other, with the tab bar `hidden`; `src/lib/contact-tabs.ts`, run from the component's `<script>`, turns them into the WAI-ARIA tabs pattern (roles, `aria-selected`, `aria-controls`, `aria-labelledby`, roving `tabindex`, Left and Right arrows, Home and End, Enter and Space, manual activation) and keeps the panel not chosen `hidden`, so its controls leave the tab order while keeping everything they hold. The chosen tab is the URL's fragment (`#book-call`, `#send-message`), written with `pushState` on a click, so direct links, fragment links on the page, and Back and Forward all choose a tab, and nothing scrolls or moves focus on a switch. A small `is:inline` script after the card applies the first choice while the HTML parses, so the page never paints both panels and then hides one. Before that it mends a link that Facebook or Instagram changed on the way in (the owner's decision, 2026-11-24): Facebook adds its click id after the fragment (`#book-call&fbclid=…`, or `#book-call?fbclid=…` when the link had no query), and Instagram's bio link percent-encodes the `#`, so there is no fragment and `utm_content` ends in `%23book-call`. The script moves Facebook's addition to the end of the query or takes Instagram's ending off its value, makes the tab's id the fragment, and rewrites the address with `replaceState` (no reload, no new history entry, the entry's state kept), acting only when the name it recovers is a tab's id. It edits the query as text, so every other parameter keeps its spelling and place. It runs while the card is parsed, and Tag Manager's container script is added only at the visitor's first interaction or three seconds after `load`, so in practice the tags read the mended address; the page then opens on the tab and scrolls to it as for a plain fragment. `fromHash` in `src/lib/contact-tabs.ts` reads a fragment's name the way the inline script does, as its part before any `&` or `?`, so `hashchange` and `popstate` agree with it. A plain script and not a Vue island for the reasons the form has: the Netlify form must stay the plain HTML Netlify detects, the state is one fragment, and the page still loads no framework runtime. Without JavaScript both panels show in turn under their own headings.

**Calendly, the contact page's third-party script.** The booking panel (`BookingCalendar.astro`, `src/lib/booking-embed.ts`) embeds the event with Calendly's documented inline embed: `widget.js` from `assets.calendly.com` is fetched once the page has loaded and the browser is idle, never before render, and `Calendly.initInlineWidget({ url, parentElement, resize: true })` is called only while the booking panel is on show, once; switching tabs hides and shows the same iframe. The event's details are hidden in the embed (`hide_event_type_details=1`, available on every plan, since the panel states them); colour options are not used (they need a paid plan) and the cookie banner and branding stay. The container is at least 320px wide at every width (the card runs edge to edge below `sm`), Calendly sets its height from the booking page, and the placeholder over it holds the "Open booking calendar" link to the same event until Calendly has shown itself; the script's failure, or twenty seconds without a sign of Calendly, leaves the placeholder with the link. Calendly keeps availability, time zones, and the booking; no API key, backend, or second scheduler exists. The embed's own cost is Calendly's: its iframe fetches about 3.6 MB of Calendly's and Stripe's scripts and styles and sets their cookies, which Lighthouse's third-party-cookies audit counts against the page, so `lighthouse.budgets.json` gives `/contact/` its own allowance for that embed and the audit script counts transfer budgets against the site's own resources only (`docs/performance.md`, "Budgets"). The page's own performance is unchanged: score 1, TBT 0 ms, CLS 0, since nothing of Calendly loads before the page has.

## Analytics: Google Tag Manager (2026-11-21)

The owner chose Google Tag Manager and gave the container, `GTM-PVBR2FJZ`, to be installed as Google's dialog shows it. The snippet is in `src/layouts/BaseLayout.astro`, straight after the `color-scheme` meta and before `<title>`, so every page carries it and it sits as high in the head as Google asks.

**The snippet as given.** Google's current one-block install (`<script async src="https://www.googletagmanager.com/gtm.js?id=GTM-PVBR2FJZ">`, then the `dataLayer` and `gtag('js', new Date())` lines), checked against Google's "Install a web container" page on 2026-11-21, which no longer has the second, `<noscript>` iframe part. Since 2026-11-22 the first of those, the script tag, is no longer in the markup; the loader described under "Deferred" below adds the same `async` script element later, and the `dataLayer` and `gtag()` lines are unchanged, so the container finds exactly the `dataLayer` it found before. Two things are Astro's. The script carries `is:inline`: without it Astro bundles the inline script as a module, so `gtag` is no global and it runs deferred (and, while the external tag was in the markup, it tried to resolve that one). And `gtag()` keeps `arguments` as written, since gtag.js tells its commands from other `dataLayer` pushes by that object and an array would not be read as one, so `eslint.config.js` turns `prefer-rest-params` off for the layout's scripts rather than ship a lint comment to every visitor. No ID, snippet, or tag lives anywhere else: tags, triggers, and the hostnames they fire on are the container's configuration in Tag Manager, not this repository's.

**What it costs, and the rule it bent (2026-11-21 to 2026-11-22).** `.cursor/rules/accessibility-performance.mdc` asks a third-party script to load after interaction or at idle; this one first loaded with the page, `async`, as Google places it, because it measures the page view and deferring it would under-count short visits and skew the timings the container records. It did not block rendering. Measured on 2026-11-21 (`docs/performance.md`): one request of about 116 KB from Google on every page and nothing more while the container fires no tags; performance 1 on mobile and desktop, TBT 0 ms, CLS 0.000, best practices as before (1, and 0.77 on `/contact/` for Calendly's cookies); under mobile throttling the contact page's LCP moved from 903 to 1052 ms as the script shares the link with the fonts, inside the 2500 ms budget. `lighthouse.budgets.json` now allows 6 third-party requests on every route (from 0), room for a Google Analytics tag and its beacons; the Calendly allowance on `/contact/` already covered the one more (17 measured of 25). A heavier container (a chat widget, a pixel, a heat map) shows up there as a failed budget, and is a new decision. The script had one more cost in the audit: on GitHub's runner, Lighthouse's simulation sometimes counted it toward the home page's LCP, the hero image, so `/` had a mobile LCP allowance of 3000 ms, removed with the deferral below (`docs/performance.md`, decision log, 2026-11-21 and 2026-11-22).

**Deferred (2026-11-22).** The owner's decision, after PageSpeed Insights on the live home page read 75 on mobile in some runs and 95 or more in others, with the difference almost all LCP (3 of 25 points in the low run, 6.0 s). The LCP element is the hero's device image, already AVIF, eager, and `fetchpriority="high"`; the cost was the race described above, now with the whole container: when `gtm.js` started before the hero's frame was shown in Lighthouse's observed run, the simulation replayed it, `gtag.js`, `fbevents.js`, and the pixel's configuration, about 500 KB in all, over simulated slow 4G before the image. So the `<script async src>` tag left the markup. The inline script keeps Google's `dataLayer` and `gtag()` lines and adds a loader that appends the same `async` script element to the head at the visitor's first `mousemove`, `pointerdown`, `keydown`, `touchstart`, or `scroll` (passive, once, then removed), or three seconds after `load`, whichever comes first, and only once. Lighthouse never moves a pointer, scrolls, or types, and its trace ends about a second after `load`, so the scripts fall outside the measurement; on desktop a visitor is counted at the first pointer movement, so the three-second window applies mostly to phones. The Meta pixel stays a container tag: an `fbq` stub and a direct `fbevents.js` load in the page were considered and rejected, since Meta's base code returns early when `fbq` exists, so the page would have to load the script itself and both copies would call `init` and `PageView`, two page views per visit. What it costs: a visitor who leaves within about three seconds of `load` without moving a pointer, pressing, typing, touching, or scrolling sends no `page_view` and no `PageView` (GA4 counts such sessions as unengaged in any case, and Meta's visitor audiences no longer gain them); engagement time reads up to three seconds shorter for a visitor who never interacts; and a visitor who taps away in the first instant may lose the first page view if `gtag.js` has not finished, so that session starts on its second page. Leads are unaffected: a lead takes interaction, which loads the tags at once, and a push made before the container arrives waits in `dataLayer` and is read when it does. Verified the same day with a one-off Playwright script outside the repository, the page served as the production hostname so that the triggers matched, only the script files from Google and Meta passed through, and every `collect` and `/tr` answered locally so that no hit reached either report: nothing third-party 2.4 s after `load`; `gtm.js` at 3.04 s after `load`, `gtag.js` and `fbevents.js` at 3.4 s, the pixel's configuration at 3.5 s, one `page_view` and one `PageView` by 3.7 s; a `generate_lead` push after that gave one GA4 `generate_lead` and one Meta `Lead` with their `lead_source`, and a push made before the container loaded gave the same from the queue; a mouse movement, scroll, key, tap, or press loaded the container within 0.5 s and the timer then added nothing; `window.gtag` exists at once and `window.fbq` once the container's tag has run; no console errors. One finding for such checks: `fbevents.js` sends nothing when the user agent says `HeadlessChrome`, with this loader and with the old snippet alike, so a check of the pixel needs a stock Chrome user agent. In Tag Assistant or the Pixel Helper, move the mouse or wait three seconds before expecting the tags. To reverse: put the `<script async src>` tag back before the inline script, remove the loader, and restore the `/` allowance in `lighthouse.budgets.json`.

## Analytics: Microsoft Clarity (2026-11-26)

The owner chose Microsoft Clarity, project `zk1wb4b735`, for heatmaps and session recordings beside GA4's statistics, and asked for it in the page itself: not as a Tag Manager tag, and not through the `@microsoft/clarity` npm package. It is the third of the site's third-party scripts, after the container and Calendly's scheduler, and the one analytics script the page loads rather than the container.

**How it loads.** The inline head script that carries Google's `dataLayer` and `gtag()` lines (`src/layouts/BaseLayout.astro`) sets Clarity's queue stub straight after them: `window.clarity = window.clarity || function () { (window.clarity.q = window.clarity.q || []).push(arguments) }`, the one line of Microsoft's snippet that has to run early. It is set on every host, so a call made before the tag loads waits in `clarity.q` and is replayed when it does; the `arguments` it pushes are covered by the `prefer-rest-params` exception `eslint.config.js` already makes for the layout's scripts. The tag itself, `https://www.clarity.ms/tag/zk1wb4b735`, is appended to the head (`async`) by `loadTagManager()`, right after the container script, so it arrives on the same trigger: the visitor's first `mousemove`, `pointerdown`, `keydown`, `touchstart`, or `scroll`, or three seconds after `load`, whichever comes first, and never before the page has painted ("Deferred" above applies to it as to the container, costs included). It is appended only when `location.hostname` is `auralinkstudio.com` or `www.auralinkstudio.com`. The GA4 tag and the pixel get that restriction from the container's "Production hostname" trigger; Clarity is not a container tag, so the page makes the check itself, and local dev, Netlify Deploy Previews, Playwright's preview, and the Lighthouse audit send no sessions. No IP filter is configured in the Clarity project; the hostname check is what keeps the owner's own local and preview visits out.

**The lead signal.** `trackLead()` (`src/lib/lead-tracking.ts`, "Lead signal" above) follows its `dataLayer` push with three Clarity calls: `clarity('set', 'lead_source', source)`, a custom tag on the session; `clarity('event', 'generate_lead')`, a custom event; and `clarity('upgrade', 'generate_lead')`, which asks Clarity to prioritize the session's recording. They go through `window.clarity?.()`, typed in the file's `declare global` block beside `dataLayer`, so before the tag loads they queue, and where the head script was blocked there is no stub and nothing is called. As with the tags, only the source travels: never the visitor's name, address, number, message, or anything from the booking.

**What it costs.** Not measured on the live site yet: the change was built and checked on 2026-11-26 before deploy, and the audit on localhost cannot see the tag by design, so `lighthouse.budgets.json` is unchanged and that day's audit of `/`, `/contact/`, and `/privacy/` (all budgets met) shows only the few hundred bytes the stub, the loader's branch, and the footer's notice add to each document. On the live site Clarity adds its tag, the script the tag then loads, and the beacons it sends while the visit lasts, Microsoft's bytes all, to the six third-party requests a visit already makes (the container, `gtag.js` and its beacon, `fbevents.js`, the pixel's configuration, and its beacon), after the first interaction or the three-second timer, so outside Lighthouse's trace unless the timer fires inside it ("Page delivery", last paragraph). The default third-party request budget of 6 was sized before Clarity and does not include it, and the audit cannot measure it, so the budget stays as it is until a live measurement says otherwise. Judge it as the pixel is judged: PageSpeed Insights on the live pages and field data. One thing to watch there: Lighthouse's `third-party-cookies` audit, which already fails on `/contact/` for Calendly's and Stripe's cookies, will count any cookie Microsoft sets from its own domains on a page where the tag loaded inside the trace.

## Page delivery (2026-11-22)

What the browser needs before it can show a page, made smaller and fewer, after PageSpeed Insights on the live home page listed the stylesheet as the one render-blocking request (27 KB, "est savings 110 ms"), a forced reflow of 56 ms in the services strip's script, a critical chain of 507 ms (page, stylesheet, then the Mukta light face), and Facebook's scripts under cache lifetimes and legacy JavaScript. Measured before and after in `docs/performance.md`. Four changes:

- **The stylesheet is inlined.** `build.inlineStylesheets: 'always'` in `astro.config.mjs` writes the one stylesheet into every page's `<head>` instead of linking `/_astro/*.css`. As a file it was the one request that blocked the first paint: the browser had to receive the page, ask for the sheet, and wait a round trip before showing anything. Inlined, the page paints as soon as it arrives, and the Mukta light face, which the browser only asked for once the sheet had applied, is asked for with the page. The cost: each page carries the sheet (about 17 KB more compressed per page), the sheet is not cached between pages, and Lighthouse's `document` transfer reads about 45 KB on the home page in the local audit (34 KB as Netlify's brotli), so its budget went from 40 to 80 KB (`docs/performance.md`, decision log). Reverse by removing the `build` block; the budget goes back with it.
- **The stylesheet is a third smaller: 185 KB to 121 KB before compression, 24 KB to 17 KB as brotli.** Two settings in `src/styles/global.css`. `@import 'tailwindcss' source('..')` collects class names from `src/` only; Tailwind 4 otherwise reads every file in the repository that git does not ignore, and the class names quoted in `docs/`, `.cursor/`, and `tests/` had put daisyUI components the site never renders (`dropdown`, `drawer`, `collapse`, `toggle`, `validator`, `dock`, `diff`, `chat`) and example utilities into the sheet, 23 KB of it. The daisyUI `exclude` list names the components the site does not use (`alert`, `badge`, `breadcrumbs`, `card`, `chat`, `divider`, `fieldset`, `footer`, `hero`, `join`, `label`, `link`, `list`, `menu`, `modal`, `progress`, `range`, `stack`, `status`, `steps`, `swap`, `tab`, `table`), 41 KB, which plain words in comments, data files, and scripts ("menu", "steps", "table") would otherwise keep pulling in, since Tailwind cannot tell a word from a class. Starting to use one of them means taking its name off the list, or it renders unstyled (`.cursor/rules/styling-tailwind-daisyui.mdc`). Checked by comparing every class in the built pages and scripts against the old and the new sheet: every class styled before is styled after.
- **The SVG favicon was a data URL until 2026-11-26, and is linked by path again.** `BaseLayout` read `public/favicon.svg` at build time and wrote it into the icon link (1.5 KB compressed per page) instead of linking the file. Chrome asks for the icon as soon as `load` fires, which on these pages was before the hero was shown, and Lighthouse's simulation then counted the request toward First and Largest Contentful Paint (`docs/performance.md`, 2026-11-22, the deferral entry: about 75 ms of the home page's mobile LCP, then the hero's device image). On 2026-11-26 the owner had the icon linked again, `<link rel="icon" type="image/svg+xml" href="/favicon.svg">` above the ICO's link, so Google Search can crawl it at its own URL. The gain no longer shows: the home page's LCP has been its heading since the device image went, and its FCP and LCP read the same with the link as with the data URL; of the sampled pages only one whose LCP is an image pays, `/about/` on desktop, 20 ms (`docs/performance.md`, 2026-11-26). Keep the icon linked (`.cursor/rules/accessibility-performance.mdc`). The ICO is linked by path for browsers without SVG icons, and both files are served.
- **No forced reflow in the strip under the hero** (the services strip then, the industry strip since 2026-11-23). Its script, now `src/lib/industry-strip.ts`, had measured the list as its first act after the page was parsed, which made the browser style and lay out the whole page then and there (902 elements, about 12 ms on a Mac and 56 ms on the live page in PageSpeed Insights), and measured again after adding the copies. The first measurement now happens in the ResizeObserver's first report, after the browser's own first layout, and the half's width is the list's times the number of copies rather than a second measurement. Same clones, same duration, same test (`tests/e2e/industry-strip.spec.ts`).

One more on the hosting side: `netlify.toml` sends `Cache-Control: public, max-age=31536000, immutable` for `/_astro/*`, the fonts, images, and scripts whose names carry their content hash. Netlify's default, `max-age=0, must-revalidate`, had the browser ask about every one of them again on each page view. Pages keep the default so a deploy shows at once. This changes nothing in Lighthouse's first-visit measurement and everything for the second page a visitor opens.

What this does not touch, and what PageSpeed Insights still lists: Facebook's `fbevents.js` and the pixel's configuration (short cache lifetimes, legacy JavaScript) are Meta's files, loaded by the container's tag; nothing in this repository can change how Meta serves them. That they were in the report at all means the container's three-second fallback fired inside the audit's trace: Lighthouse ends its trace once the page has been quiet for a second after `load`, which on the live home page from a Mac was 2.5 s after `load`, half a second before the timer; PageSpeed Insights' machines are slower and the trace can run past it, and then the container, `gtag.js`, and Meta's scripts, about 500 KB, are simulated on a throttled phone and count toward Total Blocking Time. The fallback's length is the owner's decision ("Analytics", "Deferred"): a longer one (five or six seconds) or none (interaction only) would keep the tags out of the audit, at the cost described there in page views from visitors who never interact. Recorded as an open decision below.
